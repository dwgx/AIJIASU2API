## What this release is

The third public pre-release of the **AJiaSu → API** control plane, published 2026-10-29: an
operator-run service that turns an authorized vendor account into a scoped, lease-based proxy
API. It is the first release published with release verification, build attestations, immutable
draft-first publishing, and Windows install/update scripts. The control-plane surface, SDKs and
six-asset packaging are unchanged in scope; the dashboard only gains the two copy-only update
commands. The contract stays `0.1.0` and no operation changed.

In scope:

- `ajs-accountd` control plane, operator dashboard and the public `/docs` bundle.
- The loopback data plane published only through nginx `stream` with TLS.
- The production deploy kit, the packaging script, and the Go/TypeScript SDKs.
- Release integrity: `deploy/verify-release.sh`, image digest pinning, build attestations and
  immutable draft-first publishing.
- Windows install, update, run and verify scripts under `deploy/windows/`.
- Bilingual deployment documentation (`docs/DEPLOYMENT.md`, `docs/DEPLOYMENT.zh-CN.md`).

Out of scope and deliberately off: customer portal, orders, epay/Stripe callbacks (experimental,
disabled — see [`docs/EPAY-STATUS.md`](../EPAY-STATUS.md)); multi-slot leases; high availability;
Windows/macOS service wrappers (the Windows path is a scheduled task, not a service).

**Authorization.** No written vendor authorization is on file for the live multi-user CONNECT
edge. The demo is operator-run, invite-only, educational and research-only, with no SLA, and may
be withdrawn at any time. See [`DISCLAIMER.md`](../../DISCLAIMER.md) and
[`README.md`](../../README.md#use-boundary).

## Changes since `v0.1.0-pre.2`

### Added — `deploy/verify-release.sh`

One verifier for a downloaded release. It downloads the six assets with `gh release download`
into a fresh `mktemp -d` directory (mode 700, printed as `dir:`), refuses `latest`, and checks,
in order: `SHA256SUMS` and that it covers every asset; `MANIFEST.txt` (`version` equals the tag,
`commit` is the 40-hex SHA at the tag, `worktree: clean`); then build provenance for every asset.
The release attestation is checked when present and reported `absent` otherwise.

- `--require-attestation` makes the release attestation mandatory — the strict form for an
  immutable release.
- `--allow-unverified` skips attestations only; checksums and `MANIFEST.txt` are still enforced.
- Exit codes: `0` verified, `1` failed check, `2` usage. A missing `gh` is always a failure, and
  a `gh` without `attestation verify` is a failure unless `--allow-unverified` is given.
- `--dir` is accepted only when it is owned by the current user and not group- or world-writable.

### Added — attestations and immutable draft-first publishing

`.github/workflows/package.yml` signs a build-provenance statement for exactly the six release
files with `actions/attest-build-provenance` (`id-token: write`, `attestations: write`), creates
the GitHub release as a **draft**, attaches all six assets, and only then publishes it with
`gh release edit "$TAG" --draft=false`. `.github/workflows/release.yml` attests each pushed image
by **digest** with `push-to-registry: true`, never creates a release, waits up to 10 minutes for
the draft, and then updates the notes.

Draft-first is the only order an immutable release accepts: assets are locked at publication, so
a release published before its assets exist could never accept them. The repository's
immutable-releases setting is enabled, and this release was published through that procedure: the
API reports `immutable: true`, all six assets carry build provenance, and the release attestation
verifies. The `release` workflow needed one retry — attempt 1 failed at the accountd GHCR push
with `unknown blob`, attempt 2 succeeded on the same tag and commit. That is a transient registry
transport error, not a code or pipeline defect; the pushed image digests were attested and
verified.

### Added — image digest pinning

`deploy/update.sh` resolves each pulled image's digest, verifies the attestation **for that
digest**, records both digests in `deploy/update-state.json`, and exports
`AJS_ACCOUNTD_DIGEST` / `AJS_DASHBOARD_DIGEST` so the containers that start are the exact bytes
that were verified. `deploy/compose.release.yml` accepts those variables; leave them unset to
track the tag. `--verify` is the default, `--allow-unverified` is the only opt-out (and still
resolves and records digests), and `--rollback` restores the previously recorded image IDs.

### Added — Windows install, update, run and verify scripts

`deploy/windows/` now carries `install.ps1`, `update.ps1`, `run.ps1` and `verify-release.ps1`
plus a manual. `install.ps1` verifies, installs under `C:\ProgramData\AIJIASU2API`, registers the
scheduled task `AJSAccountd` (the daemon has no SCM dispatcher), and runs a health check.
`update.ps1` verifies, stops the task and any running daemon, keeps the previous binary, swaps,
health-checks and rolls back automatically on failure; `-Rollback` restores the previous binary.
`run.ps1 -Smoke` is a throwaway loopback run with temporary state. Attestations are required by
default; `-AllowUnverified` is the only opt-out and never skips a hash. `-WhatIf` prints the plan
and writes nothing.

### Added — bilingual deployment documentation

[`docs/DEPLOYMENT.md`](../DEPLOYMENT.md) and [`docs/DEPLOYMENT.zh-CN.md`](../DEPLOYMENT.zh-CN.md)
cover the three install shapes (Linux/systemd, Compose, Windows EXE), the four verification
layers (checksums, manifest, build provenance, immutable release + release attestation), digest
pinning, the draft-first pipeline, the update card, and rollback. They also record what was
observed for the Windows scripts against `v0.1.0-pre.2` and mark the elevated path `[UNVERIFIED]`.

### Added — recorded HMC and Windows smoke coverage

The deployment docs and `deploy/README.md` state what was actually exercised: the HMC
Compose/release-pipeline checks (recorded 2026-10-23; `update.sh` run end-to-end against a fake
`docker` shim, with no pull, `up` or push) and the Windows verifier, `install.ps1 -NoService`,
`update.ps1` without auto-start, `-Rollback` and `run.ps1 -Smoke` runs against `v0.1.0-pre.2`
under PowerShell 5.1 and 7. Neither exercised the new attested pipeline, and the elevated Windows
path is `[UNVERIFIED]`.

### Changed — Settings → Updates offers two copy commands

The dashboard card now offers **Copy verify command**
(`cd deploy && ./verify-release.sh --tag <latest> --require-attestation`) and **Copy update
command** (`cd deploy && ./update.sh --tag <latest> --verify`). Both are copied for a human to run
on the host; the dashboard executes neither and there is no root update endpoint. The strict form
cannot be satisfied by `v0.1.0-pre.2` — that release has no attestations — so use
`--allow-unverified` for it.

### Fixed — `deploy/README.md` update guidance

The Compose walkthrough now states the correct `update.sh` tag requirement, the enforced order
(`gh` capability check → pull → digest resolution → verification → state file → `up` → health),
and how to handle a tag that predates attestations.

### Docs and site

`README.md`, `CHANGELOG.md`, `docs/RELEASE.md`, `docs/VERSIONING.md`, the docs index, the
current-release status lines in `docs/`, and the project page were updated for `v0.1.0-pre.3`.
`v0.1.0-pre.2` notes are unchanged and remain historical.

## Verification commands

Run against the published release:

```bash
gh release view v0.1.0-pre.3 --json isPrerelease,assets \
  --jq '[.isPrerelease, (.assets | length)]'
# -> [true, 6]

(cd deploy && ./verify-release.sh --tag v0.1.0-pre.3 --require-attestation)
# -> exit 0: SHA256SUMS 5/5 OK, MANIFEST commit 5479a3a, build provenance verified,
#    release attestation verified

sha256sum -c SHA256SUMS                     # or: shasum -a 256 -c SHA256SUMS
gh attestation verify ./ajs-accountd-windows-amd64.exe --repo dwgx/AIJIASU2API
gh release verify-asset v0.1.0-pre.3 ./ajs-accountd-linux-amd64 --repo dwgx/AIJIASU2API
gh attestation verify oci://ghcr.io/dwgx/ajs-accountd@sha256:<digest> --repo dwgx/AIJIASU2API
```

The published Windows binary prints `ajs-accountd v0.1.0-pre.3 (5479a3a)` for `-version`.

For `v0.1.0-pre.2`, the checksum path is the only one that can pass:
`./verify-release.sh --tag v0.1.0-pre.2 --allow-unverified`.

## Known limitations

1. **The live daemon is still `ajs-accountd-61625b0`.** This release does not update the live
   host. The live binary predates the 10 s entitlement watch, so revocation there still only
   stops new sessions; the live daemon also runs as root without `AJS_RBAC_STRICT`. See
   [`docs/releases/v0.1.0-pre.md`](v0.1.0-pre.md#known-limitations).
2. **No Authenticode signature.** The Windows executable and every other asset are unsigned;
   SmartScreen may ask for **More info → Run anyway**. Authenticity rests on the attestations,
   not on a platform signature.
3. **The elevated Windows path is `[UNVERIFIED]`.** Task registration, the SYSTEM launch, and the
   update-time health check with automatic rollback are code paths, not observed runs on this
   workstation. The non-elevated paths (verify, `install.ps1 -NoService`, `update.ps1` without
   auto-start, `-Rollback`, `run.ps1 -Smoke`) were run against `v0.1.0-pre.2` under PowerShell
   5.1 and 7; the published `v0.1.0-pre.3` binary itself was verified and reports its stamped
   version.
4. **No local Docker pull.** Both image digests and their attestations were verified with
   `gh attestation verify oci://…`, but this workstation has no Docker daemon, so no
   `v0.1.0-pre.3` image was pulled or started; the Compose/`update.sh` path against these images
   remains `[UNVERIFIED]`.
5. **`v0.1.0-pre.2` has no attestations.** It was published by the previous flow (the image
   workflow created the release), is mutable (`"immutable": false`), and fails closed under the
   strict verifier. Its six assets were not rebuilt.
6. **Published tags are immutable.** `v0.1.0-pre.3` is an annotated tag (`753122c`) on `5479a3a`
   and is locked by GitHub (`immutable: true`); `v0.1.0-pre.2` (`95f7930`) and `v0.1.0-pre` are
   immutable in practice because their assets are bound to the commits they were built from.
   Corrections require a new tag.
